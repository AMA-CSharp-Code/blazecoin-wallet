# Clean-machine smoke test — first live execution (2026-07-07)

Five provisioning runs against a **Windows 10 Enterprise Evaluation 22H2** Hyper-V VM
(ISO `19045.2006.220908-0225...CLIENTENTERPRISEEVAL_OEMRET_x64FRE_en-us.iso`, 5,550,497,792
bytes, fetched via the Evaluation Center fwlink `2208844`; kept at `F:\BlazecoinSmokeVM\Windows10.iso`).
Installer under test: `BlazecoinWalletV2-Setup-2.0.0.exe` (130 MB, built 2026-07-06).

## Verdict: 9/13 PASS — all install-time checks green; the 4 runtime FAILs are environmental (.NET 10 CET fail-fast on unpatched Windows 10), not wallet defects

### What PASSED (on a genuinely clean machine)

| Check | Detail |
| --- | --- |
| setup-exe-present / installer-exit-0 | silent install, exit 0 |
| app-dir / wallet-exe | `%LOCALAPPDATA%\Programs\Blazecoin Wallet V2.0` |
| daemon-beside / cli-beside | `blazecoind.exe` + `blazecoin-cli.exe` beside the wallet exe |
| conf-placed / **conf-in-local** | `blazecoin.conf` landed in `%LOCALAPPDATA%\BlazecoinV2.0` — the fresh-box datadir resolution this test existed to prove (dev box can't test it: legacy Roaming dir present) |
| **webview2-runtime-present** | the eval image genuinely lacks WebView2; the installer's silent Evergreen bootstrapper installed it — twice across runs (149.0.4022.98, then 150.0.4078.48). This was the branch Windows Sandbox could never exercise. |

### What FAILED and why (root-caused)

`daemon-autostarted`, `cookie-auth-rpc`, `ibd-began`, `webview2-rendered` — all four are downstream
of one fact: **the wallet process dies instantly on this OS image.**

- Every launch (smoke run, interactive scheduled task, manual) crashes with
  **`0x80131506` (COR_E_EXECUTIONENGINE)**, "internal error in the .NET Runtime", faulting in
  `KERNELBASE.dll` 10.0.19041.1949.
- **Not wallet-specific**: a freshly published self-contained .NET 10 hello-world console app
  crashes identically in the guest. Run from a console it prints the real message:
  **"Your Windows doesn't fully support CET. Please install all available Windows updates."**
- Mechanism (coreclr `src/coreclr/vm/threads.cpp`, `Thread::StaticInitialize`): if user shadow
  stacks (Intel CET) end up **enabled** for the process but the OS lacks the special user-mode
  APC functionality the runtime needs alongside them, CoreCLR deliberately fail-fasts. The
  2022-era 19045.2006 kernel has the half-implemented CET; current servicing fixes it.
- **`-p:CETCompat=false` does NOT avoid the crash** (verified with the hello-world): on this OS
  build shadow stacks get enabled for the process regardless of the exe's CET-compat marking,
  so a publish-side opt-out is not a fix.
- `DOTNET_EnableWriteXorExecute=0`, `DOTNET_TieredCompilation=0`, `DOTNET_ReadyToRun=0`: all
  ruled out (same crash).

**Who is affected in the real world:** CET-capable CPU (Intel 11th-gen+/AMD Zen 3+) **and** a
Windows 10 install not updated since ~2022. Any Win10 22H2 box that has taken updates since
2023, and any Windows 11 box, is fine (dev-box round-trip test passed for exactly this reason).

### 2026-07-08 — CET workaround CONFIRMED (step 1 below executed)

Ran the staged `cet.ps1` (VM booted from Off; it had not survived the night running). Results:

- `Set-ProcessMitigation -Name <exe> -Disable UserShadowStack, UserShadowStackStrictMode`
  **fixes the CLR fail-fast**: `blztest.exe` (the hello-world that crashed `0x80131506`) exits 0
  and prints. Per-exe IFEO override beats the OS-level auto-enable that `CETCompat=false` couldn't.
- Gotcha discovered en route: with the mitigation set, launching the wallet **inside the
  PowerShell Direct session** still dies — but with `0xC000027B` (stowed exception), i.e. a WinUI
  app with no interactive desktop, NOT the CET crash. Same class of trap as harness fix 3.
  Relaunched via an interactive scheduled task (`BlzCetTest`) on the auto-logon desktop:
- **Wallet ALIVE** (40s+), **6 WebView2 child processes** (UI rendering), **blazecoind
  autostarted**, `.cookie` present, and **cookie-auth RPC works** — `blazecoin-cli
  getblockchaininfo` exit 0 with `initialblockdownload: true`, 3,072 blocks / 66,000 headers
  and climbing. That is the substance of all four previously-failed checks
  (`daemon-autostarted`, `cookie-auth-rpc`, `ibd-began`, `webview2-rendered`) passing.

Evidence on `F:\BlazecoinSmokeVM\`: `cet.txt`, `cet2.txt`, `cet3.txt` (+ `cet2.ps1`/`cet3.ps1`,
`run-cet-elevated.ps1`). VM `BlazecoinSmoke` left running with the mitigation applied.

**Still open (was step 1's "if it works" tail):** decide harness policy — bake
`Set-ProcessMitigation` into the provisioning script before wallet launch (works on any image,
but masks the real-world failure) **vs** slipstream/update the ISO (tests what users actually

### 2026-07-12 — Run 7 (Win11 25H2): **PASS 13/13** — clean-machine smoke test COMPLETE

`smoke-result.json`: `"cleanMachine": true, "passed": true, "failed": 0` on host `BLZSMOKE`
(Win11 Enterprise Eval 26200.6584, fresh unattended install). All 13 checks green, including the
four that failed on the unpatched Win10 image: **no CET fail-fast** — wallet alive with WebView2
rendering (18 processes), daemon autostarted, cookie-auth RPC answering, IBD begun
(`blocks=0 headers=18000 peers=2`). The WebView2-absent bootstrapper branch proved out again
(Evergreen `pv=150.0.4078.65` installed by the installer). This closes the ROADMAP §A
clean-machine smoke-test item; the Win11-image policy (2026-07-09) is vindicated — no mitigation
needed on a current OS.

The run needed a live rescue; each intervention became a harness fix:

- **The fix-6 ESC chasers are insufficient AND ESC doesn't work** (install stalled at the same
  "Are you sure you want to quit?" modal, VHDX writes continuing underneath — the modal only
  blocked setup's final step this time). Proven on the live console via WMI keyboard injection:
  **3× ESC left the modal up; a single `N` (the No accelerator) dismissed it instantly** and setup
  finished within ~2 min. **Harness fix 7** (`Provision-HyperVSmokeTest.ps1`): Enter nudge cut to
  3×/6s, then **`N`+ESC chaser pairs every ~5s out to ~90s** (N is inert on the boot prompt and the
  unattended progress page); `ReadyTimeoutMin` default 40 → 60.
- **The host process died silently at "launching smoke test"** (transcript ends 22:07:03 on a
  remoting error): PowerShell Direct comes up during an **earlier unattend logon pass**, and the
  guest's final reboot broke `$sess` mid-`Invoke-Command` → terminating error under
  `$ErrorActionPreference=Stop` → script dead, no FATAL line. **Harness fix 9**: the whole
  inject/desktop-wait/task-start phase is now a retry loop (5 attempts) that rebuilds the session
  on any remoting failure (`New-GuestSession` helper, 30×10s), and the result poll reconnects too.
  The phase is idempotent (`-Force` everywhere), so re-running it is safe.
- **The verified-start window was too short** (task `Ready`/never-run while the fix-3 verify loop
  had already given up): explorer.exe is visible ~1–2 min before the smoke user's logon actually
  completes, and the 6-try/~90s loop expired just before it. The task was started manually via
  PowerShell Direct (guest session `Active`) and ran fine. **Harness fix 8**: the start-and-verify
  loop now retries for a full 5 minutes (20 tries).

Because the host process was dead, the result was collected by a standalone poller
(`F:\BlazecoinSmokeVM\collect-result.ps1`) — same artifact, `C:\smoke\results\smoke-result.json`
copied to `F:\BlazecoinSmokeVM\smoke-result.json` (run-5 Win10 result archived as
`smoke-result-win10-20260707.json`). VM `BlazecoinSmoke` left running (`-KeepVM`); disposable —
the next provisioning run removes it, or delete VM + VHDX manually to reclaim ~13 GB.

Fixes 7–9 are exactly the rescue applied by hand mid-run, so their core mechanisms (N dismisses
the modal; a rebuilt session + late task start works) are field-proven even though the fixed
script hasn't itself done a zero-touch run yet. Next release's smoke run validates that end-to-end.

## Harness bugs found & fixed during the runs (all in `installer\smoke-test\hyperv\`; committed `e796699`, 2026-07-12)

1. **Eval media + ProductKey ⇒ "No images are available"** (run 1 stalled at OS selection,
   VHDX never grew): Setup filters the image list by the answer-file key, and evaluation images
   cannot be selected by key. Fix: `autounattend.xml` now takes `@@PRODUCT_KEY_XML@@` (the whole
   element or nothing) and `Provision-HyperVSmokeTest.ps1` omits it for `*Evaluation` editions.
2. **Re-run file lock** (run 2 FATAL): the leftover VM's DVD drive held `autounattend.iso` open
   while the script tried to rebuild it. Fix: remove any prior VM *before* the ISO build.
3. **Interactive task silently never ran** (run 3: task `Ready`, `LastTaskResult` 267011):
   PowerShell Direct becomes reachable before the auto-logon desktop exists, and
   `Start-ScheduledTask` on an Interactive-logon task without a desktop session no-ops. Fix:
   wait for the guest's `explorer.exe`, then start the task and verify it enters `Running`.
4. **Result race** (run 3 post-mortem): the host polled for `smoke-result.json` while a manually
   launched diagnostic run was writing one, grabbed it, and tore the VM down mid-investigation.
   Mitigated by fix 3 (host only polls after a verified task start); use `-KeepVM` for any
   debugging run.
